# 项目地图

本文档描述项目的文件夹结构和各部分的职责。内容为不可变变量，禁止写入常变化还没有确定的内容。

---

## 顶层

```
Xenica/
├── README.md             仓库的入口描述
├── AGENTS.md             AI 协作的工作规则
├── .gitignore
│
├── docs/                 全部非代码文档
├── backend/              Rust 后端代码
├── frontend/             前端代码
├── scripts/              开发工具脚本
└── obsidian-assets/      Obsidian 附件
```

`docs/` 之外是代码区。当前文档体系已建立，代码部分待 L2/L3 thread 逐步建设。

---

## docs/（文档区）

```
docs/
├── about/                公开的项目说明（协作者看完这个就知道项目在干什么）
├── genesis/              🔒 划定了项目边界和基调——为什么存在、要解决什么问题
├── decisions/            所有已确认决策的 ADR，按 L1/L2/L3 层级 → thread 名组织
├── principles/           工程原则——可演进，随项目发展而增长
├── inbox/                暂时不知道归到哪的东西——有空再提炼
│   └── research/         竞品研究笔记
└── archive/              永不参考但留作记录的历史方案
```

### 公开与私有的边界

仓库变为公开或邀请协作者时：
- **保留**：`about/` `genesis/` `decisions/` `principles/`
- **隐藏**：`inbox/`
- **可选**：`archive/`

### 各目录说明

#### about/ — 项目入口

面向协作者和未来的自己。含项目概述、系统架构说明、术语表。

#### genesis/ — 边界与基调

用户手动组织语言。它不描述"怎么做"，而是定义 **Xenica 为什么存在**、要解决什么认知场景的问题、以什么理念作为设计的出发点。AI 只读——不是为了限制 AI，而是为了确保项目方向不发生语义漂移。这里的文本是后续所有 ADR 和代码的参考基准，不会被 supersede。

#### decisions/ — 决策记录

所有已确认的技术决策以 ADR 形式存放。按 `[层级]/[thread名]/` 组织，每个 thread 文件夹包含该 thread 的 scope 定义、ADR、handoff。打开 `decisions/` 的目录树就能看到整个项目的决策历史。

#### principles/ — 工程原则

通用工程原则，来自 Unix 哲学、人月神话、程序员修炼之道、Anthropic Context Engineering 以及本项目的实践讨论。一条原则一个文件，原子化。原则不是一次写死的——在开发过程中遇到新的教训、新的场景，随时新建文件加入。AI 在设计或写代码时应主动对照这些原则。

#### inbox/ — 暂存区

调研笔记、工具体验、暂时找不到分类归属的东西。可能被提炼成 ADR 或原则，也可能被删除。不做结构约束。

#### archive/ — 历史记录

v1 阶段的废弃技术方案和过时架构文档。冻结不动。

---

## principles/ 清单

具体内容见各文件。原则覆盖：设计哲学（KISS/YAGNI/概念完整性/模块化/策略分离/最小惊讶/不可变/破窗）、代码纪律（注释/编译期/尽早失败）、开发节奏（先工作再正确再快/成熟技术/同步异步）、思维层面（代码廉价/工具服务价值/地图不是领土/文档原子化分类命名）、AI 协作（上下文有限/隔离/交接压缩）。
