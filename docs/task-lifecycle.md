# 一次任务的交付流程

1. **定义**：Agent 在对话复述范围、验收场景与边界；用户确认「开始」后记录原话来源，直接实施。已有确认不重复确认，实质扩大范围才重新审核。
2. **实现与修复**：Agent 完成拆分、代码、迁移和部署。缺陷先复现；检查失败继续修复，不能把未完成部分包装成验收成果。
3. **全面自检**：所有必需检查通过；在真实部署上核对成果身份并跑端到端测试；按规格逐项实际操作，检查桌面/窄屏、刷新与持久化、错误路径、权限和冲突等相关场景。外观改变必须亲眼看截图。测试覆盖范围以规格为准，绿色 CI 不代表新需求已覆盖。
4. **交付门**：Agent 将对应提交的范围来源、全部场景、可查证据、截图检查及未解决问题写入自检报告。门禁要求当前检查全部成功且报告完整、全部通过、没有未解决问题。证据不完整保持进行中，禁止请用户找 bug。
5. **结束验收**：无需用户操作的成果经过 Agent 和机器验证后自动合并；交互成果只在自检通过后提供网址、已实现体验和操作方法。用户亲自体验并在对话确认后，Agent 记录对应成果的验收。开始确认不等于结束验收。
6. **收尾**：合并前再次核验当前成果与工程检查；更新接续索引、定义/实现/证据关联。用户退回就修复、重新自检，再交付。

## Agent 自检报告

Agent 通过仓库所有者身份在关联 PR 写 `/自检 <完整提交 SHA>`，下一行是 JSON；这是内部记录，不要求用户使用命令。字段：`schema: 1`、`source`、`artifact`（实际产物摘要）、`preview`、`scope: {confirmed: true, reference}`、`scenarios: [{name, result: "passed", evidence: [https链接]}]`、`visual: {result: "passed", evidence: [https链接]}`、`unresolved: []`。非交互成果不要求 visual。链接指向 CI 测试记录、截图构件或已有复现材料；不记录分享令牌、密码。

报告是 Agent 的可追溯实测声明，不是机器能证明“看过截图”的凭证；门禁只能机械核对身份、字段、检查结论与声明。不得伪造执行结果或把声明冒充自动测试。真实部署 `preview` 检查自动等待对应提交上线再运行浏览器回归；失败、超时或缺失不能交付。最新失败报告使旧成功报告失效。

## 永久记录与上线

当前候选预览的临时部署入口与正式上线清理步骤见 [预览接续](context/preview-bootstrap.md)；不能把预览的部署结果登记成正式推广。

`delivery-records/index.json` 串联同仓库 `records/<sha256>.json`。包含候选身份、真实检查的 run/attempt/job、部署身份、Agent 自检、用户体验验收及推广。原始设计和数据库快照在服务器持久目录中，身份、校验值与恢复入口随目录保存；原件和凭据不进公开 Git。记录写入失败即阻止放行。

产品验收内部格式是 `/验收 <完整源码 SHA> <product-id>`，下一行 JSON：`{type:"product-acceptance",quote:"用户实际原话",origin:"chat:<session>/<message>",experiencedAt:"ISO时间"}`。Agent 必须从真实用户消息取原话；范围批准不属于此类型。相同产物重跑工程检查可复用产品验收，产物改变需重新体验。

上线前核对合并后的 Git tree 与候选源 tree 完全相同，规则指纹和最新检查没有被替换。只推广已验收的 digest，不重新构建替换。先备份数据库与原始画板，失败恢复旧运行产物，永久档案和证据保留。历史启动从固定快照恢复隔离数据，十五分钟无活动释放实例。

## 版本发布

一个 Milestone 汇总体验版本的 Issue/PR，Project 的“阶段”表示任务进度，“体验版本”和“发布状态”投影 Release 事实。PR 合并不等于已上线或已发布；发布权限仍由仓库所有者控制，Agent 执行用户明确选定的版本发布。

1. 更新前后端版号、`releases/<版本>.json` 和面向人的发布说明；自检及 CI 检查一致性。
2. 完成范围内任务的机器验证、交互验收和主线集成。没有可查原话就不能登记产品验收；`experiencedAt` 保存确认时间，不冒充用户首次体验的精确时间。
3. 在 master 调用 `release.yml`，参数是版本与确切合并 SHA。控制器检查永久验收、最新检查、源码 tree 和规则，记录明确推广请求；普通合并不更新 `latest`。
4. 部署器仅接受与当前主线及镜像匹配的发布请求。保存正式数据和独立画板备份，升级两个入口，核对身份并保存持久部署回执；失败恢复原运行产物，保留数据和失败记录。
5. 控制器再次检查主线和两个部署，确认备份回执，创建 Tag 和 Release 草稿，上传带校验值的清单；验证附件后发布不可变 Release，再保存正式发布记录。看板投影失败可重跑，不能把已发布事实撤回成“未发布”。

同版本再执行只核对既有 Tag/附件并补记录，不重复部署。新版本必须使用新的版号与声明；不能移动旧 Tag 或替换附件。源提交、合并提交、镜像摘要分别保存，Git Tag 与镜像标签不混用。
