# 组件、接口与数据模型

> 从 S1/S7/S6 三条数据流中汇总推导。

## 组件

三条数据流中出现的角色只有三个：

| 组件         | 职责                      | 数据流来源    |
| ---------- | ----------------------- | -------- |
| CLI 客户端    | 接收用户命令，格式化展示结果          | S1/S7/S6 |
| API Server | 接收 HTTP 请求，执行业务逻辑，读写数据库 | S1/S7/S6 |
| PostgreSQL | 持久存储节点和边                | S1/S7/S6 |

Phase 1 **不需要**额外的 worker 或消息队列——S1/S7/S6 全部是同步操作，API 直写 PG 直接返回。

## 接口形态

三条场景的操作特征：

| 场景  | 操作性质        | 数据量        |
| --- | ----------- | ---------- |
| S1  | 写（创建节点+边）   | 单条         |
| S7  | 读（单节点+一层邻居） | 少量         |
| S6  | 读（全量节点+边）   | Phase 1 少量 |

所有操作都是**同步的、单次请求-响应**，没有长时间运行的任务。不需要异步、不需要消息队列、不需要 WebSocket。

### 推导出的 API 端点

| 端点                          | 对应场景 | 说明                     |
| --------------------------- | ---- | ---------------------- |
| `POST /nodes`               | S1   | 创建节点，可附带要连接的已有节点 ID 列表 |
| `GET /nodes/{id}`           | S7   | 获取节点详情                 |
| `GET /nodes/{id}/neighbors` | S7   | 获取该节点的所有邻居和边           |
| `GET /nodes`                | S6   | 获取所有节点                 |
| `GET /edges`                | S6   | 获取所有边                  |

端点围绕**领域动作**设计（"创建节点"、"查邻居"），不围绕表结构或 UI 屏幕。这对应旧探索 thread 中已认可的 "REST/Action" 风格。

## 数据模型

三个场景共同需要的数据形状：

- S1 需要：存一段文本（content → nodes 表），存文本与已有节点的关联（source_id + target_id + label → edges 表）
- S7 需要：查一个节点（nodes），查它的边（edges），查边的另一端节点（nodes JOIN edges）
- S6 需要：全量读取 nodes + edges

不需要额外的属性表——Phase 1 中节点只有 content 文本，不做属性分类。也不做节点类型约束——Phase 1 所有节点平等，类型是未来根据使用模式自然涌现的。

### 推导出的表结构

```sql
CREATE TABLE nodes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    content TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE edges (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_id UUID NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
    target_id UUID NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
    label TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_edges_source ON edges(source_id);
CREATE INDEX idx_edges_target ON edges(target_id);
```

### 数据模型的设计约束

**为什么是两张表：** 图数据天然是节点+边。一个节点的邻居查询（`source_id = ? OR target_id = ?`）在两张表上纯 SQL 即可完成，不需要图扩展。S7 的 "查一层邻居"不需要深度遍历，两张表就够了。

**为什么 content 是纯 TEXT：** S1 的文本输入就是一段自由文本。结构化信息（作者、日期、标签等）不预设在 columns 里，而是通过边连到其他节点表达。这避免了"每次多一种属性就要 ALTER TABLE"。

**为什么边 label 是自由文本：** S1 的连接语义是用户当场决定的——"这段教材内容 connected_to 那个概念"，label 是"connected_to"还是"derived_from"还是用户自己的命名，无法预设枚举。

**为什么不做软删除：** Phase 1 先不做。删了就真删了。需要版本/撤销时在 Phase 2+ 加入（S9 完成事项的回响、S4 代码追溯都可能催生版本需求）。

### 当前数据模型不包含的

| 项目 | 原因 |
|------|------|
| 属性表 / 类型列 | Phase 1 不需要——所有节点平等，属性通过边表达即可 |
| 递归 CTE 深度图遍历 | S7 只查一层邻居，不需要深度遍历 |
| 全文搜索索引 | Phase 1 数据量小，`content` 的直接 LIKE 搜索就够了 |
| pgvector / zhparser / pg_trgm | Phase 2+ 的 S8（跨格式同一性）和搜索需求才需要 |
