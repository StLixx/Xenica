在 v0.2.0 和 v0.2.3 的开发过程中，逐步体验到了，也对理想中的开发有了更深的理解
首先操作减少和信息聚合。举一个具体例子：当前多域名系统需要每次新开发出一个 PR，就打开对应的 PR，输入 Demo- Demo 的用户名和密码
理想状态是在在 ChatGPT Work 中打开一个固定网址，就能管理全部开发。不同的 PR 也可以保留，比如通过新开发的 HTML 嵌入到画板里，并说明这是第几个版本
关于 PR 和合并体系，在当前工作流下，这对 Agent 可能比较直观，但对人相当麻烦。想要查看，要么打开 GitHub Web 页面，一个一个点进去审核，不停地和 ChatGPT Work 页面切换

而 PR 及 Issue 之前在 V0.1.0 设计的这一套 PR/Issue 循环体系里，信息留存大部分是给 Agent 的。理想状态下，按照当前截图所示，左侧为对话，右侧为画板

画板上能看到所有页面，也就是真实正式站的所有页面；所有会出现交互的页面，包括折叠和展开，都要展示到最基础的组件及设计体系

以后可能还需要关注，并关联到具体 Feature 的原子化描述

当前还远达不到让 Opus 介入主站原生设计体系，以及主站特色 UI、UX 设计的程度。现在连开发用的脚手架，甚至用 Excalidraw 搭的脚手架都没有完成；同时，当前工作的系统信息也需要全面优化

1. 斜杠通过设计：Agent 类在执行任务时，间断、合并和不合并，以及各个版本区别、PR 和合并这样的设计是好的，CI/CD 合并也是好的

2. 网址和自动化构建：现在造成了太多网址，自动化构建也产生太多网址

3. 鉴权问题：每个网址还有单独的鉴权，但这个鉴权形同虚设，密码直接写在引导页明面上

4. 登录引导页：直接登录到 GitLab，也没有强调它实际上对应的是什么预览、有哪些功能更新、加入了哪些 Feature，以及相较于哪个版本、哪个 PR 版本进行了什么样的改进

当然值得注意的是，我说的并不是非常按照顺序和严格的语义化逻辑整理，而是暂时先想到哪说到哪

如左边所提及的，如何用当前脚手架的读取速度进行优化，以及如何让 CI/CD、当前验证和自动部署更加全面、周密，让 bug 更少发生、更早返回，并且让信息更多留存到 GitHub 仓库。也就是确认以 GitHub 仓库为唯一源，同时把我的个人偏好、我做出的决策，以及我在绘画中，特别是在绘画中做出的关键决策整理进去

未来我可能会开始完善脚手架，像现在这样，在草图画板上想到哪说到哪地进行决策。首先在 brainstorm 阶段，会在画板上把这些决策自动化布局，梳理成一个个要点。当然，不会删除我最开始所说的内容，但是会梳理成一个个要点，并且能组织出关系和关联，能看出截图与截图之间的关联，或者对应的组件、HTML 切入页面，以及之前的某个 feature。同时也希望这个能让 Agent 阅读

首先，仓库是唯一事实源，同时也是 Agent 的唯一事实源。以后我要去翻箱倒柜，或者让 Agent 查证之前是怎么决策的。因为对于目前阶段而言，这个部署脚手架还是一个非常粗糙、不持久的东西。部署到服务器上，今天可能部署到这个服务器上，明天可能部署到另外一台服务器上。而 GitHub 仓库承载着从 25 年 1 月一直到现在的稳定版本管理

好像一开始也创建了 GitHub Projects 以及相关权限，但我也不知道 GitHub Projects 有没有用。我希望在接下来全面优化我的工作流体系中，Agent 能够很好地利用 GitHub 作为核心事实唯一事实源

而 XCADDraw 搭建出来的脚手架，是面向我的精简核心。也就是面向我的交互，在里面对信息进行精简梳理，排除大量我不需要关注、或者我没有能力关注的内容，就能完成很好。比如后端，比如我刚刚提到的对工作流体系优化的要求，具体如何实现，这些技术细节不要跟我提到。

然后版本号区别于 PR：PR 主要是从 Agent 来看，它们俩可以相互独立。而版本号由我来命名、我来记忆。我根据自己的感受确定一次的开发任务量，然后它达到的版本号会有多大
