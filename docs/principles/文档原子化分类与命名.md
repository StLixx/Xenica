# 文档原子化、分类与命名

信息组织和文档管理遵循三个动作：拆、归、命名。

## 拆（原子化）

不要让一个文件承载多种信息。一个文件 = 一个主题 = 一个决定 = 一个原则。「一份文件只说一件事」——这样索引清晰、修改不会误伤、AI 不会混淆上下文。

反例：把 ADR 格式规范、目录结构、访问权限全部写进一个 README。正例：`adr-standard.md` 只说 ADR 怎么写，`docs-structure.md` 只说目录怎么排。

## 归（分类）

用文件夹树来表达归属关系，而不是把关系塞进文件名。

- `decisions/L1/v1.0.0-project-foundation/` —— 看到这棵树就知道：这是 decisions → L1 层的 → project-foundation thread 的产出（v{m} 部分是其时间线序号）
- `principles/` —— 扁平，因为每条原则是独立原子，彼此正交

分类的颗粒度：能塞进已有文件夹的就不新建。只有当前的文件夹装不下这个话题了，才建新的。

## 命名

文件名只写主题，不写元数据。元数据放进文件内容的 `##` 第一行。

- 好：`thread-layers.md`
- 不好：`L1-project-foundation-2026-07-06-thread-layers.md`

理由同「地图不是领土」——文件名是你对内容的标注，不是内容本身。把所有元信息塞进文件名就像把所有路线画在一张地图上，最终谁也看不清。主题名短到一眼就知道这个文件说什么，就够了。

> *来源：本 thread 中从 8 个 ADR 拆到 5 个的过程——核心是把信息原子化、用目录表达归属、用简短文件名表达主题，而不是把所有维度塞进命名*
