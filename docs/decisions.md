# 决策记录

只追加，不修改。被推翻的决策新增一条，并写明它推翻了哪一条。

## D-001 技术栈沿用 Rust + Axum + sqlx + PostgreSQL 17

2026-10-05 · 沿用 attempt3 的论证：成熟、AI 生成质量高、编译期检查能减少漏掉的错误分支。前端选 React + Vite，因为生态最大，Electron 可以直接复用它的构建。图视图用 React Flow 加 ELK.js，因为它们同时支持手动编辑和自动分层布局，不用自己写画布。

## D-002 契约优先

2026-10-05 · 手写的 `contracts/openapi.yaml` 是前后端之间唯一的边界，TS 类型从它生成。这样后端不会跟着前端改，换客户端也不用动后端。放弃的方案：从 Rust 代码生成 OpenAPI，因为那样契约会随实现漂移。

## D-003 数据模型：节点 + 边 + 视图，属性放在 JSON

2026-10-05 · 修订 attempt3 的「属性即节点、不用 JSONB」。原因：任务状态、时间、地点这类属性，如果都做成节点，查询和界面都会很绕。保留的口子：当某个属性值需要有自己的关系时，再把它升级为节点，通过边连接。不设 `type` 列，类型等使用中自然出现后再加。

## D-004 从第一天起为多端同步做准备

2026-10-05 · 使用 UUIDv7、墓碑删除、全局 `version` 和 `since` 增量拉取。这几项现在成本很低，以后补就要改所有表。离线编辑和 CRDT 不做，等 Desktop 或 Mobile 阶段再决定。

## D-005 位置属于视图

2026-10-05 · 同一份数据要在图、列表、日历等多个视图中保持同一性，而节点在图上的坐标只对图视图有意义，所以存在 `ViewItem` 上。

## D-006 工作方式：一会话一任务，走 PR

2026-10-05 · 每个会话只做 `tasks.md` 里的一张卡，自动化验证通过后开 PR，由用户合并。这样每个会话的上下文都短，换模型或换工具也能接着做。
