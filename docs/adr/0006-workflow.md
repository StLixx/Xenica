# 0006 工作流程

状态：已采纳 · 2026-10

## 决定

人只站在两端：说清意图、验收结果。中间由机器跑，每跑完一圈把判断沉淀成下一圈的上下文。

- **最小单位是 Issue**，四类：试样、功能、缺陷、流程（标签）。进度放在 GitHub Projects「Xenica」的「阶段」字段：收件 → 待澄清 → 规格待确认 → 就绪 → 进行中 → 待验收 → 完成。
- **主线**：Issue → 草稿 PR（= 认领）→ 机器门（CI）→ 预览 → 验收门 → squash 合并 → 主线校验。正式上线另经明确版本发布，见 ADR 0015；任务合并不代表版本发布。
- **规模决定分层**：小改动 Issue 即规格；中等写规格（`specs/`）；大的再加 ADR、拆子 Issue。开始前，Agent 在对话复述 Scope、用户确认并说「开始」，即完成范围审核，不再要求二次规格确认。仅在范围未确认时先提规格 PR；执行中实质扩大范围需另行确认。
- **交互决定体验验收**：界面或截图变化、标为需验收、fork、改已有迁移、破坏性 SQL 需要人工验收。纯工程流程和后端在已确认 Scope 内由机器及 Agent 验证，不仅因文件位于 `.github/` 就要求用户看代码；平台严格检查和负向回归不能省略。规则在 `.github/scripts/gate.cjs`。
- **结束后的验收**：后端等无需用户动手体验的成果由 Agent 与机器门验证。交互成果要用户亲自体验后确认，Agent 保存实际原话、来源及产品身份。开始不能当体验验收；用户无需操作 GitHub。相同产品重跑检查可复用验收，产物变化需重新体验；工程资格仍须对应最新规则、主线与运行尝试。
- **截图基准不进仓库**：master 的 CI 在 Playwright 官方容器里给每个 story 截图，存为构件；PR 下载来比。合并即更新基准。
- **部署只拉不推**：core-server 上的部署器每 2 分钟从 GitHub API 和 ghcr 拉取。GitHub 不需要服务器的任何权限；fork 提的 PR 推不了镜像，所以不会有预览。
- **沉淀**：每个 PR 填「沉淀」一栏，优先变成检查和测试。`AGENTS.md` 不超过 200 行（CI 检查）。

## 理由

- 用户在任何设备、任何 AI 上都能提 Issue，在手机上点预览、评论 `/通过` 就能验收；所有执行都走同一条管线，不依赖聊天记录。
- 打扰用户的情况：意图或 Scope 尚未确认、执行中实质扩大范围、交互成果需体验或改动撤不回；已在对话确认的 Scope 不重复审核。

## 后果

- 用 GITHUB_TOKEN 合并不会触发 push 事件，所以验收门合并后手动触发一次 master 的 CI。
- 验收门的规则改动必须在确认的范围内，增加相应负向回归；若改变用户定义的批准边界则需重新确认范围。
- 用户自己也能随时手动合并；规则集要求「验收」状态通过，所以手动合并也要先 `/通过`。
- 以后再做：每周度量（提报到上线的时长、打扰次数、拦截率）、分诊 Agent、应用内反馈。

## v0.2.5 已发布

验收记录由 Agent 代写 `/验收 <完整提交 SHA> <product-id>`，附真实原话和来源；兼容带身份的 `/通过`。旧命令、旧检查或来源不完整时不放行。候选、检查、自检、验收、部署备份和发布记录保存在独立永久分支。发布规范工程与已验收的首次发布产物分开集成，不移动既有 Tag。
