# 0015 体验版本与正式发布

状态：已采纳 · 2026-10-13

用户决定一次发布 v0.2.5，并将版本与审批流程正式化；整体体验通过，UI/UX 优化进入下一版。参考讨论：<https://chatgpt.com/s/cx_6acd96ad690881919c2325e90badf0f9>。

- Commit 固定修改，Branch 承载任务，PR 是合并单位。体验版本可汇总多个 PR；Milestone 定义范围，Project 投影任务与版本状态。
- 合并只集成并校验。明确发布操作核验已合并提交与已验收源 tree 相等、最新工程资格及规则指纹；只推广同一镜像，先备份，核验正式站和独立持久画板。
- 版本声明与前后端一致。正式 Tag 指向合并提交；不可变 Release 附带验收源、合并源、镜像、规则、检查与持久部署回执。失败不标已发布，同版本重跑验证身份后不重复部署或覆盖附件。
- 用户的“开始”只批准 Scope；交互验收取实际确认原话及来源。无需用户操作的工程成果自动验证；改审批流程也须有负向回归和平台强制检查，不以额外 GitHub 人工操作取代会话验收。

首次发布冻结已体验产物，不为追加流程文件重建它。后续工程规范另经 PR 进入主线，不移动 v0.2.5 Tag。v0.2.3 的另一份产物未定位，保留为待核实记录，不推断包含关系。

GitHub 的不可变发布锁定 Tag 与附件，不能锁定外部镜像标签或可编辑说明；所以仍使用镜像摘要及附件校验。[GitHub 官方说明（Tier S）](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
