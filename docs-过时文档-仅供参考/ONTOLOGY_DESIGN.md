# Xenica 本体论设计

**状态：设计阶段（待 SQLite 迁移完成后实现）**

---

## 一、现有架构

| 组件 | 当前状态 |
|------|----------|
| 数据模型 | 认知瞬间（moment）+ 实体（entity）+ 关系边（relates_to / evolves_from） |
| 实体类型 | person / concept / work / place / event / term（6 种，LLM prompt 约定） |
| 关系类型 | semantic / temporal / sensory（3 种，计划增加 tension、Source 节点类型等） |
| 建边方式 | LLM 从对话/笔记中抽取实体和关系，写入数据库 |
| 检查方式 | 目前全靠 LLM |
| 存储 | ~~SurrealDB~~ → SQLite + sqlx（编译期 SQL 检查） |
| 语义搜索 | embedding 向量（sqlite-vec） |

---

## 二、本体论与现有设计的关系

### 现有设计 = 类型标签 + 存查

- 实体/关系类型作为标签使用，用于分类存储和展示
- 不做类型校验、不做规则推理、不做自动合并

### 本体论 = 在同一套类型上加规则和推理

- **纠错**：类型/关系超出枚举直接拒绝；不合法的边（如"人→位于→地点"）自动拦截
- **推理**：子类包含（查"概念"自动含"学科"）、传递性（A≈B、B≈C → A≈C）
- **统一**：同名/同义实体合并，减少重复节点
- **边权**：不同关系类型赋不同权重，避免 hub 节点吸走所有 PageRank

---

## 三、三层关系

| 层 | 功能 | 查询方式 |
|----|------|----------|
| 图数据库 | 存"谁和谁有什么关系" | 按关系查、沿边遍历 |
| 向量 / Embedding | 存"谁和谁意思像" | 按相似度搜索 |
| 本体论 | 在类型和关系上加规则手册 | 按规则纠错、推理、统一 |

**本体论不替代图或向量，是在两者之上加一层基于含义的校验和推理。**

---

## 四、本体论能解决的痛点

| 痛点 | 本体论解决方式 |
|------|----------------|
| LLM 有时乱写类型 | 枚举校验，超出直接拒绝，不依赖 LLM 再检查 |
| 同一实体被拆成多个节点 | 同名+同类型规则合并/对齐 |
| 明显不合常识的边 | 约束规则：谁能和谁用哪种边连，违规即拦 |
| 建边/检查全靠 LLM，成本高慢 | 确定性规则处理类型校验/约束/合并，只把语义判断留给 LLM |
| 错误难追溯难修 | 规则写在代码里，拒绝/合并可打日志，比"LLM 说不对"好排查 |

---

## 五、为什么不用 OWL 推理器

| 考量 | 选择 |
|------|------|
| 编译期检查 | OWL/RDF 是运行时字符串，无法享受 Rust 编译器 QA |
| 可调性 | 规则直接改 Rust 代码，和调 PageRank 一样，适合产品迭代 |
| AI 可写性 | 枚举+校验函数训练数据充足，AI 写正确率高；写完整推理器训练数据不足 |
| 无额外依赖 | 逻辑全在 Rust，数据全在 SQLite，导出/迁移不依赖 OWL 格式 |

与 SurrealDB → SQLite 的决策链**完全同构**：
- 编译期检查 > 运行时字符串
- 嵌入式 > 独立服务
- AI 训练数据充足 > 冷门工具

## 六、实现方案

在 backend 加一个小模块（如 `ontology` 或 `graph_rules`）：

```rust
// 示意结构
mod ontology {
    // 枚举固定实体类型、关系类型（和 LLM prompt 对齐）
    pub enum EntityType { Person, Concept, Work, Place, Event, Term }
    pub enum RelationType { Semantic, Temporal, Sensory, Tension, Evolution }
    
    // 校验函数：建边前检查
    pub fn validate_edge(from: &Entity, to: &Entity, rel: RelationType) -> Result<(), ValidationError>;
    
    // 合并策略：同名实体检测
    pub fn find_mergeable(new_entity: &Entity, existing: &[Entity]) -> Option<EntityId>;
    
    // 边权配置
    pub fn edge_weight(rel: RelationType) -> f32;
}
```

工作流程：
1. LLM 抽取实体和关系
2. **过本体论校验**（类型枚举、边约束、同名检测）
3. 通过则写入 SQLite，拒绝则返回错误或自动修正

## 七、本体构建算法（让本体"自己长"）

半自动方式：
1. 算法从笔记/对话中提议新类型或约束
2. 用户确认后纳入本体
3. 新规则写入代码，单元测试锁住行为

**不建议"一次写对不用审"**——作为初稿+迭代基础足够可靠，但需要人工审核关键决策。

## 八、与 ARCH.md 12 项改进的对应

| 改进项 | 本体论对应 |
|--------|------------|
| 缺 tension 边、Source 节点 | 类型体系中加新边类型/节点类型，定义约束 |
| PageRank 边权（不同边类型权重不同） | 给每种边类型赋权重（或范围） |
| 实体 understanding_history、视角层级 | 给实体/视角加属性结构或子类型 |
| Moment 粒度、精炼迭代 | 用演化边（evolves_from）+ 约束 |

当前后端仍需重构（SurrealDB → SQLite + sqlx），本体论作为新后端的一部分，而非在旧架构上叠加。

---

## 十、关键结论

1. 本体论**不是替代 LLM 建边**，而是把"能写成规则"的部分从 LLM 手里接过来，更省、更稳、更好修
2. 按 Xenica 技术栈逻辑，选**轻量 Rust 自实现**而非 OWL 推理器
3. 本体设计可以用 **vibe coding 做初稿**，配合测试和人工审核保证可靠性
4. 本体"自己长"用**半自动方式**：算法从笔记提议，人确认后纳入
