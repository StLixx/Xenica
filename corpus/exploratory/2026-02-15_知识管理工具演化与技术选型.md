## 数据库选型最终决策

**结论：SQLite + sqlx 替换 SurrealDB**

### 决策逻辑链
1. 用户开发方式是 vibe coding（AI 写代码，用户验收）
2. Rust 编译器是免费的第零层 QA → 数据库客户端必须支持编译期检查
3. sqlx 的 `query!` 宏是唯一提供编译期 SQL 验证的方案 → 只有 SQLite/PostgreSQL 支持
4. 嵌入式需求 → SQLite
5. 向量搜索 → sqlite-vec 扩展
6. 图遍历 → 递归 CTE，封装成 5 个函数后调用方无感
7. PageRank → AI 实现，后台定时跑，结果缓存

### 关键数据
- 30 年知识量上限估算：~70 万节点，300-500 万边
- SQLite 在此规模下所有常用操作 < 50ms（人不可感知）
- SQLite 理论上限 281TB，实际占用 ~1-2GB

### 排除的选项
| 选项 | 排除原因 |
|------|---------|
| SurrealDB | 运行时字符串查询（无编译期检查）、SDK bug（Thing 序列化）、训练数据少 |
| CozoDB | Datalog 更小众、无编译期检查、pre-1.0 |
| Neo4j | JVM 重（~1GB 内存）、非嵌入式、Rust 客户端非官方 |
| ArangoDB | 非嵌入式、无编译期检查 |

### 边生成机制（8+ 条通路）
- 对话共建（~75%）、向量语义检索（~25%）
- 结构化导入（书/课本内在结构）
- 错题归因、错误模式聚类、题型同构、跨域同构
- 双链导入、时空共现、感官触发、目标关联

### Markdown 备份策略
- SurrealDB = 源头 → 改为 SQLite = 源头
- 每日凌晨导出 JSON/Markdown 到 OneDrive 同步目录
- Markdown 是灾难恢复和技术迁移用的逃生舱，不是数据源

## 补充洞察

### 边的保真度是核心需求
- 用户最在意的不是数据库性能/稳定性，而是"对话结束后图谱里的每条边是否准确反映认知关联"
- 这是 X2 提取流水线（LLM prompt）的质量问题，不是数据库问题
- 需要"AI 建议建边 → 用户在对话中自然确认/拒绝"的交互机制

### AI 写标准算法的可靠性
- PageRank、图遍历等经典算法：AI 写正确率极高（训练数据充足 + 可单元测试验证）
- 真正风险在设计层：建什么边、怎么排序、多种信号怎么融合 → 产品迭代问题
- 自写实现比内置黑盒更适合需要不断调整的产品

- 未来：SQLite 后端就绪后，这些 markdown 作为种子数据导入
